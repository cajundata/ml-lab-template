- **`gpu_up` intentionally leaves you in `stranded`.** That is its whole purpose — it is the debug path, and it prints a handoff block ending in "Do not power off this droplet. Destroy it." But it means an operator who runs `make gpu-up`, gets distracted, and closes their laptop is burning GPU-hours until the 2h TTL. The self-destruct timer bounds the damage; it does not eliminate it.
- **A hung benchmark burns up to the full TTL.** `validate_timeout_budget` guarantees SSH + bootstrap + benchmark *fits under* the TTL, but nothing caps the actual spend below it. The 1800s benchmark timeout is the real bound in practice.
- **`LabDropletExistsError` means one stranded droplet blocks every future run.** This is intentional (it forces you to look), but if you are hitting it, the answer is `make gpu-audit` and then `make gpu-down` — never a workaround.
- **The `booting` state is the longest and least observable.** `pip install vllm` drags in torch and CUDA, and it is the bulk of the up-to-1800s bootstrap window. If a run is mysteriously slow, it is almost certainly here. `pull_artifacts` fetches `/var/log/cloud-init-output.log` as `bootstrap.log` precisely because this is where things go wrong and the evidence dies with the droplet.
